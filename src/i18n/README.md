# Internationalisation (English + Hindi) — customer app

Strategy and rules for every Proviyaa app: `docs/I18N.md`. Hindi terms: `docs/I18N_GLOSSARY.md` (use those exact words).
Where the work stands: `docs/I18N_STATUS_customer-app.md` (generated by `npm run i18n:check`).

## Add a string to a screen (the whole routine)

1. Write the text in a fragment file, English and Hindi side by side, and add it to both catalogues in one step:

   ```json
   { "cart": { "emptyTitle": { "en": "Your cart is empty", "hi": "आपका कार्ट खाली है" } } }
   ```
   ```
   npm run i18n:add -- fragment.json        # writes en.json AND hi.json; refuses mismatched {{placeholders}}
   ```
2. Use the key in the screen:

   ```tsx
   import { useTranslation, useFormat } from '@/src/i18n';
   const { t } = useTranslation();
   const fmt = useFormat();
   <Text>{t('cart.emptyTitle')}</Text>
   <Text>{t('cart.total', { amount: fmt.money(total) })}</Text>      // "Total {{amount}}"
   <TextInput placeholder={t('cart.notesPlaceholder')} accessibilityLabel={t('cart.notesLabel')} />
   ```
3. `npx tsc --noEmit` fails on a misspelt or missing key (keys are typed from `locales/en.json`).
4. `npm run i18n:check` — parity, placeholders, and a list of any text you left hard-coded.

Pick the language in the app: Profile → Language. Developers can also choose **Pseudo (en-XA)** (development builds only):
every translated string shows accented and in `[brackets]`, so anything still plain English is hard-coded, and
anything that breaks when text grows ~35% will not survive Hindi.

## Rules

- **Keys**: `feature.thing` (camelCase), at most three levels: `cart.title`, `checkout.error.noAddress`. One namespace
  per feature (`auth`, `home`, `cart`, `orders`, `tracking`, `address`, `profile`, `help`, `search`, `common`, …).
  Shared words (Save, Cancel, Retry) live in `common` — reuse them.
- **English text is the original wording, verbatim.** Moving a string must not change what English users see.
- **Never join sentences from pieces** (Hindi word order differs): use `{{placeholders}}`:
  `"Deliver to {{place}}"`, not `t('deliverTo') + place`. Plurals: `items_one` / `items_other` and `t('cart.items', { count })`.
- **Numbers, money, dates, distance, minutes** come from `useFormat()` (`fmt.money`, `fmt.date`, `fmt.eta`, `fmt.distance`, `fmt.deliveryTime` for the server's "10 min" text…):
  ₹ with Indian grouping (₹1,23,456), Latin digits by default (also in Hindi), dates in India time (Asia/Kolkata).
  Never `toFixed`, `toLocaleString`, or a template with ₹ in a screen.
- **Codes are not words.** Order status, payment status, payment method and API errors arrive as codes:
  `t(orderStatusKey(order.status))`, `t(paymentStatusKey(p))`, `t(paymentMethodKey(m))`, `useErrorMessage()(error)`.
  An unknown code shows a neutral label, never the raw code.
- **Catalogue content stays as the API returns it** (product, store, brand, category names, descriptions). Do not put
  those in the catalogue. When the API gets translations per item (`content_translations`), switch the screen to the translated field.
- **Outside a component** (an Alert, a thrown error, a notification): `import { t } from '@/src/i18n'` and call it when
  the text is needed — never at module load (that freezes the language the app started in). Module-level lists of labels
  should keep KEYS and call `t()` while rendering.
- **Layout for Hindi** (~20-30% longer, taller glyphs): no fixed `height` on buttons, rows or inputs (use `minHeight`);
  `lineHeight` at least 1.35 × `fontSize` (`safeLineHeight()`); do not force a label onto one line with `numberOfLines={1}`
  unless a truncated label is acceptable. Check the screen in pseudo-locale.
- **Acronyms stay Latin** in Hindi (UPI, GST, OTP, EMI, QR, PIN). Brand names stay as written (OneLocal, One Local).
- An `// i18n-ignore` comment on (or above) a line tells the checker that string is not for translation (a developer-only error, say).

## How the pieces fit

| File | Job |
|---|---|
| `locales/en.json`, `locales/hi.json` | The catalogues. Same keys in both. English is bundled; Hindi is loaded on demand. |
| `locales.ts` | The language registry: code, native name, sample line, how to load it. Add a language here. |
| `loader.ts` | The switcher's state machine (idle → loading → ready / error, 8 s timeout, last choice wins, atomic swap). Pure, tested. |
| `runtime.ts`, `provider.tsx` | Start-up (saved → phone → English, before the first screen), the shared i18next instance, announcements. |
| `format.ts`, `hooks.ts` | ₹ / distance / minutes / date formatting; `useFormat`, `useErrorMessage`. |
| `codes.ts` | Order/payment status, payment method and API error codes → catalogue keys. |
| `language-picker.tsx`, `first-run.tsx`, `profile-sync.tsx` | The Language screen UI, the first-launch chooser, and the mirror into `profile.language`. |
| `pseudo.ts` | The dev-only en-XA pseudo-locale. |
| `fonts.ts`, `typography.ts` | On-demand Devanagari fonts (none needed today) and the web font stack / line-height helper. |

Checks: `npm run i18n:test` (loader, formats, fallbacks, status mapping) and `npm run i18n:check` (catalogues + hard-coded scan).
